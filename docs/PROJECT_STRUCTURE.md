# Project Structure

This is the single source of truth for **where a file belongs**. If you are unsure after
reading this, copy the layout of the nearest existing feature rather than inventing a new one.

The repository is a monorepo: the Flutter client lives in `lib/`, the NestJS server in `api/`.

## Flutter client (`lib/`)

```text
lib/
├── main.dart                 # Entrypoint: bootstraps Firebase, providers, router
├── firebase_options.dart     # Generated by flutterfire — do not edit by hand
├── core/                     # Anything shared by two or more features
│   ├── config/               # App-wide constants and environment config
│   ├── engine/               # Astrology engines (API, mock) + their models/
│   ├── providers/            # Global Riverpod providers (profile, theme, locale, ...)
│   ├── routing/              # go_router routes
│   ├── services/             # Platform/3rd-party integrations (Firebase, Razorpay, ...)
│   ├── theme/                # Colors, tokens, decorations, animations, components
│   ├── utils/                # Pure Dart helpers, no widgets (responsive, zodiac)
│   └── widgets/              # Shared UI widgets (GlassCard, GradientButton, ...)
├── features/<feature>/       # One folder per product feature
│   ├── data/                 # Repositories, DTOs, models/, local caching
│   ├── providers/            # Riverpod providers scoped to this feature
│   ├── services/             # Feature-only services (e.g. PDF report generation)
│   └── presentation/
│       ├── screens/          # Full pages, one screen per file
│       └── widgets/          # Widgets/painters/modals used only by this feature
└── l10n/                     # app_language.dart, app_localizations.dart, translations/
```

### Rules

- A widget used by **more than one** feature moves to `lib/core/widgets/`. A widget used by
  one feature stays in that feature's `presentation/widgets/`.
- Providers go in `features/<feature>/providers/` — never inside `presentation/`,
  which is reserved for UI.
- Helpers that import `flutter/material.dart` only for `BuildContext` extensions still belong in
  `core/utils/`; anything that renders belongs in `core/widgets/`.
- Never import across features (`features/a/...` must not import `features/b/...`). Promote the
  shared piece to `core/` instead.
- Prefer relative imports inside a feature and `package:AstroSaathi/...` imports in `test/`.
- File names are `snake_case.dart`; screens end in `_screen.dart`, widgets in `_widget.dart`
  or `_modal.dart`, painters in `_painter.dart`, providers in `_provider.dart`.

## Flutter tests (`test/`)

`test/` mirrors `lib/`:

```text
test/
├── app_widget_test.dart              # App-level smoke tests
├── core/                             # Tests for lib/core/**
└── features/<feature>/               # Tests for lib/features/<feature>/**
```

Run with `flutter test`.

## Developer scripts (`tool/`)

One-off scripts executed with `dart run tool/<script>.dart` (e.g. `tool/audit_lib_files.dart`,
which reports leftover `old`/`backup`/`temp` files in `lib/`). Scripts never ship in the app
bundle, so keep them out of `lib/`.

## NestJS server (`api/`)

```text
api/
├── src/
│   ├── main.ts               # Nest bootstrap
│   ├── app.module.ts         # Root module wiring every feature module
│   ├── <module>/             # One folder per domain module
│   │   ├── <module>.module.ts
│   │   ├── <module>.controller.ts    # HTTP layer only, no business logic
│   │   ├── <module>.service.ts       # Primary business logic
│   │   ├── dto/              # Request/response and canonical models
│   │   ├── interfaces/       # Contracts implemented by providers/engines
│   │   ├── engines/          # Deterministic math, no Nest/HTTP dependencies
│   │   ├── providers/        # External data sources (API, local, mock)
│   │   ├── processors/       # BullMQ queue consumers
│   │   ├── services/         # Supporting services beyond the primary one
│   │   └── validators/       # Input/data integrity checks
│   ├── core/                 # Cross-module services (time, location, monitoring)
│   └── database/             # TypeORM entities/, seeds, database.module.ts
├── db/                       # SQL dumps and fixtures for local development
├── .env.example              # Template — copy to api/.env, which is git-ignored
└── docker-compose.yml        # Postgres + Redis for local development
```

### Rules

- Controllers handle transport (routing, guards, validation) and delegate everything else.
- Astrology math lives in `engines/` and stays framework-free so it can be unit tested directly.
- Tests are `*.spec.ts` placed next to the code they cover (e.g.
  `src/astrology/services/astrology-accuracy.spec.ts`). Run with `npm test`.
- Entities live in `src/database/entities/` and are named `<table>.entity.ts`.

## Generated, ignored and secret files

These are intentionally **not** in git; `.gitignore` and `api/.gitignore` cover them:

| Path | Why |
| --- | --- |
| `api/node_modules/`, `api/dist/`, `api/tsconfig.tsbuildinfo` | Reproducible from `npm ci` |
| `api/.env` | Real credentials — commit `api/.env.example` instead |
| `api/database.sqlite` | Local dev database |
| `api/astrology_api_error.txt`, `*.log` | Runtime debug output |
| `android/build/`, `build/`, `.dart_tool/` | Build artifacts |

Add new configuration keys to `api/.env.example` (with a placeholder value) in the same
commit that starts reading them.
